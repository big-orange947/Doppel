# Doppel 开源开发路线

更新：2026-11-11。目标保持为长期个人 Agent 的个人记忆与上下文中枢。
比赛适配和模型渠道验通不再是当前工作的前置条件。

## 第一阶段：整理可用的个人记忆主线

让接入者能从包根 API 跑通证据写入、结构化个人记忆、时间查询、授权读取和持久化恢复。
明确区分可信结构化导入、模型提案与已确认事实，避免示例把直接 `put` 说成自动抽取。

本轮交付：[持久化个人记忆示例](personal-memory-walkthrough.md)。这是已有能力的参考接法，
不构成新的自然语言理解、质量分数或默认模型晋级。

已补充 [可恢复增量流程](incremental-personal-memory.md)，组合 miner、proposal writer、
consolidation 和 index maintenance，在执行副作用前持久化提案／整理计划，并验证重启重放。
默认演示仍使用合成 analyzer 和目录测试替身；下一步替换真实 provider／索引，接入 MemoEcho
离线历史回放，再验证在线增量写入；无需真实 QQ 压力流量。迟到事件与跨进程 lease 仍需 host 设计。

当前按用户选择继续合成数据；已增加可选治理阶段，把显式时间归档接入持久化计划和索引维护。
合成验证覆盖计划取消、撤回、多次更新、临时状态过期及重启恢复，不作为抽取质量成绩。

已增加 [到达队列与冻结批次补处理配方](late-arrival.md)，在明确接入队列的路径中发现迟到消息，
保留原时间和来源，独立重放并确认进度。旧 Store 时间游标不自动获得该能力；多实例 lease、
上下文抽取质量、队列保留策略和真实 PG 联测仍待后续验证。

## 第二阶段：写入与检索的一致性

优先验证记忆新增、纠正、撤回、归档、恢复后，词法／向量／关系候选与权威 Store 的一致性。
覆盖重启、索引暂时失效和并发写入；失败应可观察、可恢复，旧索引不能使已撤回记忆重新有效。
使用现有协议进行增量维护，先确定缺口，再决定是否扩展 API。

已完成首轮 [维护与恢复修补](index-maintenance.md)：扫描后重新加载权威记录，检查写入期间
的源变化，校验 exact-scope 身份及索引回执，失败页保留原进度。SQLite 重启恢复采用模拟
索引目录验证；实际 PostgreSQL／Graphiti 的远程故障和多实例验收仍待后续完成。

主检索路线采用词法与向量互补，再进行重排和 Store 复核。图关系保留为可选增强，
按关系、多跳任务的增益与建设成本决定是否启用。保留本地模型和可替换 provider，
不把比赛的统一模型约束变成开源框架要求。

## 第三阶段：端到端记忆质量

评测覆盖从消息进入到长期事实演变、检索及证据交付的完整过程，分别记录：

- 抽取是否遗漏信息，是否混淆说话者、事实、建议与计划；
- 整理是否正确处理更新、冲突、重复经历与时间区间；
- 候选召回、排序和材料装配分别损失了哪些证据；
- 上层回答模型能否利用这些证据，以及评分口径是否可靠。

复用已有诊断工具，但不继续围绕已打开的 LongMemEval 小样本调参。
新增留出样本和通用变体，禁止领域词典、题号规则或金标提示进入运行时代码。
已有开发集 40/50 与 reserved 9/10 继续单独解释，不能当作整体产品准确率。
扩展测评先测单项成本，再按预算扩大，不恢复全量昂贵建图。

## 后续功能

质量和可靠性收敛后，再推进任务级上下文选择、主人管理记忆的 API／可视化界面、
文档补充以及显式共享记忆策略。授权由可信 host 决定；主 Agent／子 Agent 编排仍由应用负责。
PyPI 发布继续后置，版本发布应附可复现示例、迁移说明、已知限制和实际验证范围。

## 当前不作出的承诺

目前仍是 Alpha，没有给出正式发布日期。接口测试、检索小样本、LLM 抽取质量和线上可靠性
属于不同证据；任何一项通过都不能替代其他项。保留此前比赛代码、缓存和实验记录，
不为切换开发方向删除历史数据或回退已实现能力。
