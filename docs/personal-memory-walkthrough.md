# 持久化个人记忆：最小闭环

在仓库根目录运行：

```powershell
.\.venv\Scripts\python.exe -m examples.personal_memory
```

默认使用专用示例库 `data/examples/personal-memory.sqlite3`，无外部 API、模型或 Docker
依赖。可用 `--database PATH` 指定另一份示例库。重复运行复用幂等键；不会删除数据库。
请使用单独的示例路径，避免把合成记录写入正式用户记忆库。

## 这条流程做了什么

1. 将两条 owner 原话通过 `ingest` 写成持久化原始证据。
2. 用低层 `put` 导入 host 已审核的两条结构化个人记忆，记录主体、权威、有效期及原始证据引用。
3. 关闭客户端，建立新的 SQLite 客户端后查询，验证读取不依赖旧客户端的内存。
4. 输出命中的记忆 ID、内容、时间、权威和从 Store 重新加载的原始证据。

示例采用固定时钟：2026-11-01。两条合成事实分别是“一月至五月工作地点在上海”与
“六月起工作地点在杭州”。预期输出：

| 查询 | 应返回 |
|---|---|
| 当前工作地点 | 杭州及对应原话 |
| 2026-03-01 有效的工作地点 | 上海及对应原话 |
| 仅授权空的会话 B | 空集合 |
| host 显式授权读取会话 A 与 B | 杭州及对应原话 |

这验证的是提供明确结构和权限后的保存、过滤与证据读取行为，没有自然语言抽取或自动纠正。
历史记录与当前记录的有效区间由 host 预先审核提供；示例没有根据一句话自动修改旧记忆。

## 哪些由 host 决定

`StructuredQueryPlanner` 是一个结构化工具／表单适配示例：把调用方明确传入的
`temporal_view`、`as_of` 与检索文本交给现有查询引擎。它不识别中文问题，也不对
“工作地点”设置特判。真实自然语言接入可替换为现有 reference Planner 或自定义 Planner。

同样，示例的 `put` 是受信任的直接写入 API，不会验证内容真实性或自动取得 owner 确认。
未经审核的 LLM 抽取应走 proposal／policy 流程，不能照搬这里的 confirmed 写法。
来源引用可读取，也不等于系统已验证了语义蕴含。

跨会话读取由 host 在认证和授权之后传入完整 scope 列表。框架不因查询者自称“主人”
就扩大权限；知道 scope 的值也不代表有权限。这里不做 user-scope 提升或共享策略。

## 如何继续接入

用真实事件适配器替代两条合成消息，再接入 analyzer 和 proposal writer，接着验证
整理、治理与索引的增量更新。在这些环节可靠后，按需要组合语义检索、重排和图增强。
本示例的 SQLite 词法结果不代表高配置检索质量，也不生成 Agent 最终回答。
